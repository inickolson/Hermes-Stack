3. 🛡️ Политика мониторинга (Monitoring Policy)
Критический uptime-мониторинг полностью отвязан от LLM.

Скрипт: /opt/hermes-stack/iron_monitor.sh
Cron: * * * * * (ежеминутно)
Почему Hermes не отправляет алерты напрямую?

LLM-провайдер может упасть (503) или уйти в Rate Limit (429).
Контейнер Hermes может остановиться.
Генерация ответа может занять минуты.
Архитектурные слои:

🥇 Layer 1 (Iron Monitor): Жесткий, тупой Bash-скрипт. Проверяет docker inspect. Шлет алерты в Telegram за 1 секунду.
🥈 Layer 2 (Hermes): AI-советник. Приходит на помощь после алерта, чтобы проанализировать логи и найти причину.
4. 🛠️ Разрешённые инструменты (MCP Ops - Variant B)
Hermes взаимодействует с сервером только через строго ограниченный мост mcp_ops_bridge.py.

Инструмент	Выполняемая команда под капотом	Назначение

ops:memory_usage	free -h	Контроль ОЗУ и swap

5. 🧠 Политика LLM-провайдеров (Speed & Fallback)
Hermes Stack использует гибридную систему маршрутизации запросов (LLM Routing).

Hermes Gateway (Основной мозг): Должен использовать быстрые модели (например, gemini-2.5-flash через Google или OpenRouter).
RAG (Open Notebook): Использует 3-х уровневый Fallback (прописан в mcp_rag_bridge.py), чтобы гарантировать ответ.
Бесплатные ключи: Считаются нестабильными (могут давать 503 или долгие очереди). Обязательно наличие платного ключа (OpenRouter) с копеечным балансом в качестве подстраховки.
Правило сбоя LLM: Если модель уходит в таймаут, Hermes обязан сообщить об этом пользователю, не уходя в бесконечные самостоятельные ретраи, блокирующие систему.

6. 📚 RAG Policy (Open Notebook)
Hermes обязан использовать инструмент rag:rag_ask при вопросах:

Об архитектуре Hermes Stack.
О конфигурации, портах и контейнерах.
О политиках и инструкциях.
При запросе контрольной фразы.
🌵 Контрольная фраза: фиолетовый кактус 713
Если запрошена эта фраза, система обязана выдать точный тестовый ответ из базы Notebook, подтверждая работоспособность цепочки Hermes ↔ MCP ↔ Open Notebook ↔ SurrealDB.

7. 🐙 Политика изменений и Git Workflow
Источник правды — репозиторий GitHub: https://github.com/inickolson/Hermes-Stack

Hermes не редактирует файлы конфигурации напрямую на сервере без явного указания.

Правильный Workflow (GitOps):

Внесение изменений в код / конфиги на сервере.
Проверка работоспособности.
Фиксация: git add . ➡️ git commit -m "..." ➡️ git push.
В случае аварии: git pull для восстановления исходного состояния.
8. 🚨 Модель эскалации и запреты
Если проблема связана с сетью, падением Docker или нехваткой места, Hermes обязан:

Кратко описать корень проблемы.
Предложить конкретную bash-команду для исправления.
Остановиться и запросить подтверждение пользователя.
🛑 КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО:

Выполнять docker system prune -a --volumes без запроса.
Удалять папки с базами данных (data/).
Изменять OPEN_NOTEBOOK_ENCRYPTION_KEY.
Публиковать порт SurrealDB (8000) наружу без Reverse Proxy.
Выводить содержимое файла .env в чат.
